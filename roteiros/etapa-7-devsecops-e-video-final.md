## Pipeline Stop Conditions

| ID | Stop Condition | Required Evidence | Action Before Resuming | Responsible Role |
| --- | --- | --- | --- | --- |
| SC01 | Any security test that protects authentication, authorization, input validation, session revocation, or room-state workflow fails in CI or local release verification. | Failed test output, affected requirement or risk reference, and changed files involved in the failure. | Block merge or release, fix the implementation or test expectation, rerun the focused test, and attach passing evidence. | Development Team |
| SC02 | `npm audit --omit=dev` reports an unresolved high or critical runtime dependency vulnerability, or a dependency is added without a lockfile update and review. | Audit output, dependency name and version, advisory severity, and package-lock diff. | Upgrade, remove, replace, or document an accepted exception with mitigation and responsible approval before continuing. | Development Team and Security/Operations Team |
| SC03 | Code review or repository scan identifies a hardcoded secret, unsafe SQL built from request values, missing server-side authorization on a protected route, or logging of passwords, JWTs, reset tokens, full CPF values, or payment data. | Review comment, scan output, or diff reference showing the unsafe pattern and affected file. | Remove the secret or unsafe pattern, rotate any exposed credential if applicable, add or update tests, and rerun validation before resuming. | Development Team |

Iuri segment script: "HospedaTche is a hotel accommodation system with Guests, Receptionists, Managers, Administrators, and an external payment provider. Because the system handles accounts, CPF data, bookings, payments, chat, reviews, and internal operations, security starts during planning. We mapped assets, actors, trust boundaries, STRIDE threats, and abuse cases before defining risks. In the accounts area, the most important identity risks include fake registration, account takeover, mass account creation, password recovery misuse, unauthorized profile access, and missing audit evidence. Stage 3 turns that analysis into architecture decisions. For SR01, the system must require step-up authentication before changing password, email, or CPF, and must revoke previous sessions after password change or recovery. In the DevSecOps pipeline, a change only moves forward when it stays connected to a known risk, has an observable security requirement, and appears in the architecture evidence."

Sidnei segment script: "In the implementation phase, security requirements SR01 and SR03 are converted directly into secure coding practices and pre-written TDD security tests. For identity management, we enforce strict Zod schema validation to reject malformed input or SQL injection attempts before database queries, store passwords using bcrypt with cost factor 10, require step-up authentication for sensitive account updates, and increment the account auth version to invalidate old JWT sessions upon password change. For room maintenance operations, we enforce server-side role validation and transactional state checks, ensuring rooms with open maintenance issues remain unavailable for booking until an authorized closure with immutable audit logging occurs. Our unit and integration tests, such as ST01 through ST04, verify both valid operations and malicious attempts before code is accepted into the pipeline."

Lara segment script: "In the automated analysis step, HospedaTche should not rely only on manual review. The pipeline must run security tests, check dependency advisories, and review code patterns that are connected to our previous risks. A change stops if a security test fails, if a high or critical runtime dependency vulnerability remains unresolved, or if review finds a hardcoded secret, unsafe SQL built from request input, missing server-side authorization, or sensitive data being logged. These gates connect the secure coding work, the vulnerability verification evidence, and the final release decision."

Dyonathan segment script: "In the dynamic verification stage, we used OWASP ZAP 2.17.0 to perform an authorized automated security scan against our local HospedaTche environment. The scan generated several alerts, and the group selected three relevant findings for analysis: a Content Security Policy configuration issue, a missing anti-clickjacking header, and a missing X-Content-Type-Options header. For each finding, we stored execution evidence, analyzed the possible impact, related it to OWASP or CWE references, and proposed a correction. This stage shows that security verification is not limited to reviewing code: the running application must also be tested.

After deployment, security continues through monitoring. In Stage 6, we defined which authentication, authorization, business, payment, error, and audit events should be recorded and created detection rules for suspicious behavior. When an alert occurs, the team should validate the event, investigate the affected resource and actor, preserve relevant evidence, and apply the appropriate containment or escalation procedure. This closes the DevSecOps cycle by connecting dynamic verification before release with continuous monitoring and incident response during operation."

Rafaela segment script: "To close our presentation, we see how security was woven into every phase of HospedaTche. Starting from STRIDE threat modeling in Stage 1 and risk prioritization in Stage 2, every architectural decision in Stage 3 and code implementation in Stage 4 directly responded to a concrete threat. In Stages 5 and 6, we verified that security must be validated both before deployment with automated scanners like OWASP ZAP and continuously during runtime through intrusion detection rules and structured incident response.

The greatest lesson learned throughout this project is that security cannot be an isolated afterthought or a late checklist: it must be a continuous engineering culture (Shift-Left DevSecOps). By establishing automated quality gates, enforcing strict input sanitization, server-side role validation, and eliminating single points of failure, HospedaTche ensures that guest privacy, payment integrity, and hotel operations remain resilient against modern cyber attacks."
